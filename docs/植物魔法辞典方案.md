## 二、技术选型

### 为什么不用原版成书直接塞内容

成书（`written_book`）单页上限 256 字符、14 行，而且：

- 不能显示物品图标
- 不能显示合成表
- 989 页要拆成几十本书，玩家体验割裂

### 选定方案：**CE GUI 索引 + 原版成书阅读**

分两层，各用擅长的东西：

```
[辞典物品] 右键
      ↓
[索引界面]  箱子 GUI（CE 的 BukkitInventory 那套）
   ├ 章节列表（11 个按钮）
   ├ 词条列表（每页 28 个）
   └ 点击词条 → 打开对应的"书"
      ↓
[阅读界面]  原版 written_book
   ├ 前一页 / 后一页（客户端原生翻页）
   └ 文末"返回目录"（点击成书里的文字跳转）
```

理由：

- **索引**用箱子 GUI —— 可以放 246 个词条、有图标、能搜索，体验比书好
- **阅读**用成书 —— 玩家能像真书一样翻页，客户端原生支持，不需要我们自己画界面
- 配方/图片页**文字化**成 `材料 ×数量 → 成品`，虽然不如原版美观，但信息完整

### 不采用的方案

| 方案 | 否决理由 |
|---|---|
| 自己画 GUI（物品栏摆图标） | 一页只能塞 5~6 行字，74,000 字要几千页 |
| CE 的 `image` 做页面贴图 | 需要客户端 mod 或大量图片资源，且不能选中文本 |
| Patchouli 移植 | Patchouli 本身是 mod，服务端没法跑 |

## 三、数据结构

### 1. 内容转换（工具脚本）

`tools/gen_lexicon.py`：

```
patchouli_books/lexicon/en_us/entries/**.json    （246 个词条）
        +
build/upstream_lang/zh_cn.json                   （正文文本）
        ↓
plugin/src/main/resources/data/lexicon/
    ├── categories.json      11 个章节（id / 名称 / 图标 / 排序）
    ├── entries.json         246 个词条（id / 章节 / 标题 / 图标 / 页列表）
    └── pages/<entry-id>.json  每页的渲染指令（见下）
```

单页渲染指令（插件侧解释执行）：

```json
{"type":"text",     "lines":["这是一段说明……","第二段……"]}

{"type":"recipe",   "station":"crafting",
 "grid":["活石","活石","活石","","魔力珍珠","","活石","活石","活石"],
 "result":"魔力池 ×1"}

{"type":"recipe",   "station":"mana_infusion",
 "input":"铁锭 ×1", "mana":3000, "catalyst":"（无）", "result":"魔钢锭 ×1"}

{"type":"spotlight","item":"botania:endoflame","lines":["萤火之焰","会烧掉附近的可燃物……"]}
```

### 2. 文本预处理

上游正文里有 Patchouli 的标记语法，需要清洗：

| 上游写法 | 处理 |
|---|---|
| `$(item)铁锭$()` | 取纯文本"铁锭" |
| `$(l:basics/welcome)点击这里$()` | 转成"［点击这里］"（暂不做跳转） |
| `$(br)` `$(br2)` | 换行 |
| `$(li)` | 转成 "· " |
| `$(bold)…$()` | 取文本（成书不支持样式嵌套） |
| `$(6)…$()` 颜色代码 | 去掉 |

## 四、交互设计

### 索引界面（箱子 GUI，6 行 = 54 格）

```
┌──────────────────────────────────────────┐
│ [入门][魔力][产能花][功能花][工具][装置]   │ ← 第一行：章节
│ [饰品][末影][精灵][挑战][杂项]  [搜索]     │
├──────────────────────────────────────────┤
│                                          │
│   当前章节的词条列表（每格一个词条）        │ ← 2~5 行：词条
│   图标 = 词条代表物品                      │
│   名称 + lore = 词条标题 + 一句话简介      │
│                                          │
├──────────────────────────────────────────┤
│ [上一页]                    [下一页]      │ ← 第六行：翻页
└──────────────────────────────────────────┘
```

- 章节按钮点击 → 切换到该章节，词条列表刷新
- 词条点击 → 生成并打开对应成书
- 「搜索」→ 聊天框输入关键词，过滤词条（P2）

### 阅读界面（成书）

- 每页对应上游 1 页
- 文本页：正常文本
- 配方页：`材料 ×数量` 逐行 + `→ 成品`
- 末尾加一页「§l返回目录」，点击文字跳回索引

## 五、工作量评估

| 阶段 | 内容 | 预估 |
|---|---|---|
| **P0 骨架** | 数据转换脚本 + 章节/词条索引 GUI + 纯文本阅读 | 主体 |
| **P1 配方页** | 278 条 crafting + 58 灌注 + 43 花药台 + 17 符文 + 20 酿造 的文字化 | 中等 |
| **P2 增强** | 搜索、书内跳转、图片页用物品图标替代、章节解锁进度 | 视需要 |

### P0 的交付物

1. `tools/gen_lexicon.py` —— 上游 JSON + 语言文件 → 插件资源
2. `ledger/`（插件包）：
   - `LexiconData.java` 加载章节/词条/页面
   - `LexiconGui.java` 索引界面（复用 CE 的 BukkitInventory）
   - `LexiconBook.java` 成书生成
   - `LexiconListener.java` 右键打开、点击处理
3. `botania:lexicon` 物品加行为：右键 → 打开索引

### 会让它"能跑"的最小闭环

只做 **491 个文本页 + 20 个章节索引**，其余页面类型先显示"（本节暂未收录）"。
这样 246 个词条全都能点开、能翻页，剩下的配方页按章节逐步补。

## 六、风险与对策

| 风险 | 对策 |
|---|---|
| 成书单页 256 字符上限，上游有超长段落 | 按句子切分到多页，页首标"（续）" |
| 上游 74,000 字里有大量 `$(...)` 标记 | 转换脚本里写完整清洗规则 + 输出报告列出未识别标记 |
| 章节解锁（上游有 `advancement` 门槛） | P0 全开放；P2 再做进度 |
| 索引 246 个词条分页 | 每页 28 格 × 3 行，共 9 页，够用 |
